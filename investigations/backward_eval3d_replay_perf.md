## Context

Goal: reduce Vulkan eval_3D backward cost while preserving CUDA parity and exact production replay order.

Baseline evidence from `harmonyos_3dgs/reports/backward_split_baseline_20260518_3step_cam0/vk_train.log` on NVIDIA Tegra Thor, basketball cam0, `N=400000`, `R≈1.98M`:

|---:|---:|---:|---:|
| 1 | 139.840 | 81.164 | 221.004 |
| 2 | 136.673 | 4.329 | 141.002 |
| 3 | 126.447 | 5.450 | 131.898 |

Steady-state backward is raster-dominated; preprocess backward is about 4–5 ms after first-step setup.

## Reference behavior

CUDA reference reviewed under `/home/robota/h00813233/Graph/AAA-Gaussians/submodules/diff-gaussian-rasterization/cuda_rasterizer/backward.cu`:

- EVAL_3D raster backward walks contributors in reverse compositing order.
- For each contributor it computes `plane_x = row0 - row3 * pix.x`, `plane_y = row1 - row3 * pix.y`.
- It computes `power = -0.5 * max_contrib_ray(plane_x, plane_y, max_pos)`, then `G = exp(power)`, `alpha = min(0.99, opacity * G)`.
- Contributors below alpha threshold are skipped; depth clipping uses `dot(row2, max_pos)` and `dot(row3, max_pos)`.
- Color, opacity, and transform gradients are accumulated with atomics.
- `preprocessCUDA_3D` is per-Gaussian and does not do this per-pixel replay work.

The Vulkan production replay shader `src/vulkan/shaders/rasterize_backward_eval3d_replay.comp` implements the same hot-loop math and replay order.

## Replay-sideband constraint

`src/vulkan/shaders/rasterize.comp` writes `replay_order_gids` only for contributors that forward actually blended, after power/alpha/depth checks pass. `src/vulkan/rasterizer_vulkan.cpp` builds replay offsets from `n_contrib`, so replay backward sees blended contributors in exact per-pixel order, not raw tile candidates.

Therefore tile-shared sorted batching from `rasterize_backward.comp` is not safe for production replay mode: replay order is per-pixel sideband data, and neighboring pixels may have different replay lists.

`gs3d_vk_train --eval_3d 1` defaults `--parity_mode` to true, so the 3-step split benchmark without an explicit `--parity_mode 0` dispatches the non-replay tile-sorted eval_3D backward shader. That path was tested with a `rasterize_backward.comp`-style shared-memory batch for row0/row1/row3/opacity, but the measured steady-state result stayed at ~111 ms, so the shared-memory rewrite was not retained.

## Safe optimization hypothesis

Within replay mode, preserve replay order and math but remove redundant work:

1. Reuse the cross product `d`, vector `m`, `d²`, `m²`, and `1/d²` computed for `maxContribRayPixel` in the later gauss2screen gradient block.
2. Since `replay_order_gids` contains only already-blended contributors, do not re-run the forward reject gates in replay backward. This removes the row2/depth-clip load entirely and avoids branches that can only reject entries not present in the replay sideband.
3. After removing depth clipping, do not compute `max_pos`; replay backward only needs the ray distance and transform-gradient intermediates.
4. Keep alpha, background, and atomic gradient formulas unchanged.

Conclusion: local arithmetic reuse, shared row caching, and replay workgroup-size changes were not enough for the requested 3x. The apparent 4x4 replay speedup was invalid because the shader still advanced pixel coordinates by 16 while running 4x4 workgroups, skipping most pixels. Corrected 4x4 and 8x8 coverage stayed near the restored production replay baseline. Alpha/G replay sideband tape is also rejected because it increases forward capture and backward time. The clean non-tape replay no-atomics diagnostic below shows enough headroom if the dominant atomics can be reduced, so the next implementation should focus on reducing `dL_dgauss2screen` atomic fan-in without per-hit dynamic grouping or per-hit global sorting.

A subgroup same-`gid` coalescing experiment for `dL_dgauss2screen` compiled and passed the targeted correctness gate, but regressed production replay to `211.415 / 211.269 ms` in `reports/backward_split_subgroup_g2s_coalesce_20260518_3step_cam0/vk_train.log`. The dynamic subgroup ballot/shuffle loop is too expensive for this workload and was removed.

A bounded workgroup shared-memory hash table for `dL_dgauss2screen` also compiled and passed the targeted correctness gate, but regressed production replay to `172.835 / 173.846 ms` in `reports/backward_split_shared_g2s_20260518_3step_cam0/vk_train.log`. The per-hit shared float atomics plus hash-table probing/flush overhead were still slower than direct global atomics, so the experiment was removed. Future atomic reduction should avoid per-hit dynamic grouping and avoid replacing one contended atomic path with another contended shared-memory atomic path.

An opt-in sorted reduction path (`GS3D_EVAL3D_SORTED_G2S=1`) also compiled and passed the targeted correctness gate, but regressed production replay to `493.217 / 496.844 ms` in `reports/backward_split_sorted_g2s_20260518_3step_cam0/vk_train.log`. Emitting one record per replay hit preserves exact replay semantics, but sorting roughly 1.98M records adds hundreds of milliseconds, so per-hit global sort is not a viable atomics replacement.

No workgroup-size reduction is retained. The first 8x8 and 4x4 replay measurements were invalid because the shader still used 16-pixel coordinate strides after the local size changed, skipping most pixels. After correcting the replay shader to use `gl_WorkGroupSize` for pixel mapping, 4x4 measured `130.529 / 128.670 ms` and 8x8 measured `128.086 / 130.678 ms`, so smaller workgroups did not provide a meaningful speedup over the restored production replay baseline.

An opt-in fused production replay experiment (`GS3D_EVAL3D_FUSED_REPLAY_BWD=1`) compiled, passed default targeted tests (`VkVsCudaFirstLoss|RasterizerBackwardVulkan|BackwardPipeline|TrainingStepVk`, 16/16), and passed opt-in eval_3D trainer tests (`VulkanTrainer.Eval3D*`, 4/4). It writes final geometry gradients directly from the replay shader and records preprocess eval_3D with geometry writes skipped so SH/raw-opacity gradients still use the existing shader. Basketball cam0 measured `115.999 / 113.340 ms` raster backward and `120.931 / 115.448 ms` total backward on steps 2/3. This is a real but small improvement over the restored production replay baseline, not the requested 3x; it suggests that simply moving the gauss2screen chain into the per-hit replay shader replaces the bridge atomics with similar final-gradient atomic pressure plus extra per-hit geometry math.

These results rule out moving invariant scalar setup, per-workgroup dynamic batching, mean-only intermediate elimination, static scale/rotation striping, per-hit coefficient-table geometry evaluation, hot-GID sharded final-geometry accumulation, per-dispatch world-to-screen UBO precomputation, splitting fused replay into separate mean/color/opacity and scale/rotation replay passes, fused replay local-size changes, exact per-pixel run coalescing, SoA/padded atomic target layout, tangent-only raw-rotation accumulation, subgroup pair coalescing, wider subgroup coalescing, vectorized `gauss2screen` row loads, sparse `d_g2w` math, color/opacity live-range code motion, `scale_modifier == 1` identity specialization, scalarized local `d_R` loops, inline tangent dot products, scalarized color/opacity recurrence, 8-lane mean-only subgroup coalescing, horizontal 4x1 quad swizzling, vertical 1x4 quad swizzling, same-GID row-load broadcasting, same-GID parameter-load broadcasting, direct color/opacity atomics, black-background-only specialization, black-background plus sqrt-UBO specialization, inverse raw-quaternion length math alone, black-background plus inverse-length specialization, clustered subgroup full-quad reductions, leader-only final-geometry chain evaluation, exact-zero `G` fast-path branching, exact zero-pixel-gradient fast-path branching, exact-zero atomic elision, size-focused SPIR-V optimization, one-float-per-Gaussian raw inverse-length buffering, full-tile quad-state specialization, fused-path `dL_dgauss2screen` clear skipping, subgroup-only descriptor updates, shader SSBO `restrict` qualifiers, tangent-rotation Adam fusion, skipping overwritten preprocess clears, no-pack padded intermediate tangent scratch, device-local geometry-gradient target placement, and skew-aware delayed geometry atomics as sufficient levers for the <=80 ms goal. The best validated safe path is currently around `90–93 ms` (`90.106 / 92.954 ms` in the latest recovery run), still roughly 10–13 ms above the <=80 ms success gate. The color+opacity no-atomics diagnostic shows that optimizing those atomics alone is insufficient. Scale-vs-rotation diagnostics show rotation atomics are the larger single remaining atomic class (`90.940 / 91.100 ms` if removed) and scale atomics are smaller (`98.709 / 98.004 ms` if removed), but deleting either class alone still misses the target. A combined no-rotation-plus-color/opacity diagnostic measured `72.479 / 72.026 ms`, so the target is reachable only by reducing those costs together with correct gradients. A temporary replay-gid concentration diagnostic in `reports/backward_split_replay_gid_hist_20260519_3step_cam0/vk_train.log` found about 86.1M replay hits over about 160k unique contributing Gaussians; top 1% of contributors carried about 38.4% of hits, top 5% about 70.3%, top 10% about 81.4%, and top 20% about 89.8%, but the hot-GID sharded scratch experiment proved that replacing direct final atomics with another contended atomic/reduce path is not viable. Deep research after the <=80 ms goal reset reviewed the CUDA hierarchical backward asymmetry as a possible new direction: CUDA's StopThePop hierarchical path can walk forward and reconstruct the remaining color from `pixel_colors - T_final * bg`, while the retained Vulkan fused replay shader walks the exact replay sideband in reverse with `accum_rec` / `last_alpha` / `last_color`. This is not a credible <=80 ms single-variable lever for the retained path: it would require adding a rendered-image SSBO to the fused tangent binding and changing the replay traversal/expression order, while only replacing the color recurrence and adding rendered-image loads/divisions. It does not reduce the already measured dominant final mean/rotation/color/opacity atomic pressure, and it risks changing the exact training trajectory through a different floating evaluation order. The next viable candidate must reduce rotation-related per-hit geometry atomic contention together with color/opacity and/or mean atomic pressure, or avoid equivalent per-hit geometry work entirely, without adding hash-table probing, global sorting, striping/reduction passes, duplicated full replay passes, local-size tuning, per-pixel consecutive-GID run coalescing, SoA atomic target packing, hot-GID scratch atomics, narrow black-background specialization, forward-order recurrence rewrites, or replay-order/reduction-order changes.

Structural packetization diagnostics after the <=80 ms goal reset used the retained raw replay sideband files `build/vk_replay_order_offsets_cam0.raw` and `build/vk_replay_order_gids_cam0.raw` (`691200` pixels, `89462968` replay hits, max `465` hits/pixel). Fixed pixel regrouping within each tile by first-K replay signatures was worse than the natural retained 2x2 mapping: retained natural 2x2 gives `69914091` atomic groups (`21.851%` reduction), while tested sorted/bucketed fixed schedules reached only about `19.2–20.0%` reduction. This rejects simple static pixel remapping as a practical lever.

A stricter dynamic same-reverse-depth tile packet estimate remains theoretically useful but implementation-risky. Grouping all 16x16 tile pixels by the current reverse replay depth and same GID gives `47915057` pack4 packets (`46.441%` reduction vs raw hits, average `1.867` lanes/packet), not the higher no-depth grouping bound. Relative to the retained natural 2x2 grouping, this is only a `31.466%` further group reduction (`69914091 -> 47915057`). Even with zero packet-build and zero barrier overhead, applying that reduction linearly to the measured wrong-gradient atomic diagnostics would save only about `6.275 / 6.674 ms` from the combined rotation+color+opacity classes, or about `9.011 / 9.625 ms` if the no-mean diagnostic is also included as optimistic atomic headroom. That leaves an optimistic `83.411 / 83.610 ms` raster time from the `92.422 / 93.235 ms` fallback profile, still above the <=80 ms gate before any packet control cost. It would also require at least about `365.6 MiB` of compact packet payload for `(gid + four local pixel IDs)`, about `4–5 MiB` of tile-depth offsets, and per-tile recurrence state for `T`, `accum_rec`, `last_alpha`, and `last_color` (minimum about `8 KiB` for 16x16 pixels before packet scratch). The workload has `544524` tile-depths with work, about `201.7` reverse-depth iterations per tile on average and `465` max, so an exact packet shader would likely need many per-depth barriers and deterministic packet formation. A no-depth grouping bound is much larger (`23379371` pack4 packets, `73.867%` reduction), but it is invalid for the retained reverse recurrence because it would delay or reorder per-pixel replay updates. Independent design review therefore rejects a full dynamic packet table as the next production implementation candidate.

Nsight Compute is installed but exposes CUDA-kernel profiling options, not Vulkan compute shader counters. Fresh-eyes residual sweep after packetization rejection found no remaining credible shader-local or algorithmic <=80 ms lever under exact trajectory constraints. Independent algorithm review concluded the retained fused tangent-subgroup path has already exhausted the safe same-order in-shader reduction families; any further mathematical win would require relaxing the reduction-order/trajectory constraint or changing the replay recurrence architecture. A benchmark-boundary review noted that timestamp-based split timing could honestly separate GPU intervals from `vkQueueWaitIdle` drain cost, but this would change the reported metric and is expected to recover only small single-digit milliseconds, not the required `12–13 ms`, and `total_bwd_ms` would remain the guardrail.

The one fresh Vulkan-side candidate was memory type/residency. Tegra Thor exposes storage-buffer-compatible memory types `type0 DEVICE_LOCAL`, `type1 DEVICE_LOCAL|HOST_VISIBLE|HOST_COHERENT`, and `type2 DEVICE_LOCAL|HOST_VISIBLE|HOST_COHERENT|HOST_CACHED`; the current `VulkanBuffer` picks type1, so the retained path is not using non-device-local system memory. A direct HOST_CACHED preference experiment changed `findHostVisibleMemType` to prefer type2 and rebuilt `build_release_train`. Basketball cam0 preserved the expected trajectory (`loss=0.056394/0.052083`, `R=1982943/1980899`) but measured only **92.223 / 91.959 ms** in `reports/backward_hostcached_20260521_3step_cam0/vk_train.log`, still far above <=80 and mixed against retained noise (`90.106 / 92.954 ms` recovery, `92.422 / 93.235 ms` fallback profile). The allocator change was reverted. A minimal opt-in pure-device-local geometry-gradient target experiment then moved only fused replay raw geometry outputs (`d_means3D`, `d_scales`, `d_rotations`) behind `GS3D_EVAL3D_BWD_DEVICE_LOCAL_GEOM_GRADS=1`; default and opt-in focused gates passed 20/20 and the benchmark preserved trajectory, but timing regressed to **96.170 / 96.477 ms** in `reports/backward_device_local_geom_20260521_3step_cam0/vk_train.log`, so the opt-in allocator/staging code was reverted. A standalone pure-device-local tangent-scratch probe then moved only hot `d_rot_tangent` behind `GS3D_EVAL3D_BWD_DEVICE_LOCAL_TANGENT_SCRATCH=1` and cleared it inside the raster command buffer; default and opt-in focused gates passed 20/20 and the benchmark preserved trajectory, but timing was only **93.062 / 91.311 ms** in `reports/backward_device_local_tangent_scratch_20260521_3step_cam0/vk_train.log`, so the opt-in allocator/scratch code was reverted. A broader pure-device-local rewrite for color/opacity/tangent scratch remains theoretically distinct, but the measured residency probes now make it a low-confidence high-effort direction unless new memory-counter evidence appears.
